## Research question
Research question explored by this project is:

**Can an LLM act as a semantic transition operator improving given solutions in a PSO-like optimization loop,
while retaining the cognitive/social dynamics of PSO?**

A brief example that evaluates this idea is the following example:

## Family PSO LLM Optimizer
The goal of this project is to demonstrate how a PSO-like search loop can be combined with LLM proposals to optimize a multi-member family shopping plan.
The optimizer selects products from Kaufland offers catalog, evaluates every proposed plan with a deterministic fitness function, and writes the best plan as a result into JSON format.

## Disclaimer
This project is an illustrative research prototype. It explores how LLM proposals can be combined with a PSO-like optimization loop. 
It has not been validated as a reliable solution for real-world family budget or shopping optimization, and its outputs should not be 
treated as financial, nutritional, or purchasing advice.

## What is optimized
Project aims to optimize grocery shopping for a family of five, with each member having different preferences and dietary needs. 
The configured family has five contiguous basket blocks:
| Member | Items | Preference keywords |
| --- | ---: | --- |
| father | 12 | beer, meat, grill, sausage |
| mother | 12 | vegetables, fruit, salad, organic produce |
| daughter | 10 | chocolate, candy, biscuits, dessert |
| son | 10 | chocolate, snacks, chips, cola |
| mother-in-law | 11 | detergent, cleaning, household products |

Together these blocks form one flat position of **55 item IDs** (12 + 12 + 10 + 10 + 11). 
Items' IDs may repeat because the same catalog product can be selected for more than one family member. 
The LLM is shown the block layout so it can keep each part of the flat position associated with the appropriate member.

## PSO (like) optimization algorithm
#### Initialization 
1. N particle are introduced to compete for the best solution. Each particle has a current position (set of proposed item IDs), a personal best position, and the swarm has a collective best position.
2. Every present particle position is initialized independently (seeded random position) and evaluated via fitness function.
3. Each particle's personal best is chosen along with initial collective best.
#### Iteration
4. For each iteration, ask every particle's LLM for a complete next position.
5. Evaluate the returned position and update the particle's personal best when its fitness improves.
6. Update the collective best when any proposal improves the swarm score.
7. Record the proposal in `IterationRecord` and stop after the requested number of iterations or after the configured stagnation window.

## LLM prompting and response
- On every iteration, for each particle, one prompt is sent to the LLM, which returns back a new vector of 55 catalog IDs. 
- The prompt contains: current vector, particle's personal best vector, swarm's global best vector, and complete candidate catalog. 
- The prompt also contains four **influence percentages** that guide how much the LLM should consider each component of the above vectors.
- The response is each particle's coordinates. It is a vector of 55 catalog IDs, generated by the LLM. One update replaces the whole vector.

#### What the **influence percentages** mean
The percentages are **soft instructions to the LLM**, not Python-controlled edit percentages.
- **Current-position share:** tells the LLM how much useful information it may preserve from the current vector.
- **Cognitive/personal-best share:** tells the LLM how much useful information it may take from this particle's best vector.
- **Social/swarm-best share:** tells the LLM how much useful information it may take from the best vector found by any particle.
- **Exploration share:** tells the LLM how much it may search for new catalog items that are not present in either best vector.

The response is accepted only when it contains exactly 55 integer IDs and every ID exists in the candidate catalog. If the response is invalid, the new vector is the unchanged current vector.
After the vector is accepted, the optimizer calculates its fitness. If the new fitness is lower than the particle's previous best, the particle's personal-best vector is replaced. 
If it is also lower than the swarm's best fitness, the swarm's global-best vector is replaced. The next iteration repeats this process using the updated vectors.

## Fitness function
The objective estimate of the proposed set of item IDs is given by corresponding fitness function. 
It is defined as a weighted sum of all items' prices and corresponding health penalties. The optimizer seeks to minimize the fitness value. The formula is:
```text
fitness = total_price + 1.2 * total_health_penalty
```
Health penalty is computed per item from configured healthy keywords matched in its product and category text. Each item contributes a value from `0.0` to `1.0`; more healthy keyword matches reduce that value. Repeated IDs contribute repeatedly to both price and penalty.
Health score is a lightweight keyword proxy, not a nutritional or medical assessment.

## Output
The script stores the results in `data/family_pso_plan.json` by default. The output contains:
- run metadata and completed iterations;
- the global best complete position;
- the winning particle; and
- each particle's best proposal split into the five member baskets, including product, category, price, and currency details.

## Setup and usage
The implementation of PSO steps is in `family_pso_optimizer.py`, with the LLM integration in `particle_llm.py` and some utility functions in `utils.py`. 

Install the complete project dependencies listed in `requirements.txt`:
```powershell
py -m pip install -r D:\Research\pso_llm_optimizer\requirements.txt
```
Set a GitHub token for Copilot API access, then run the optimizer from the repository root:
```powershell
$env:COPILOT_GITHUB_TOKEN = "<your-token>"
py -u .\family_pso_optimizer.py
```
Simple example:
```powershell
py -u .\family_pso_optimizer.py `
  --country DE `
  --iterations 10 `
  --num-particles 3 `
  --max-candidates 220 `
  --output .\data\family_pso_plan.json
```
Use `py -u .\family_pso_optimizer.py --help` for the complete option list.

## How GitHub Copilot calls are used
The optimizer uses the GitHub Copilot SDK (`github-copilot-sdk`, imported in Python as `copilot`) for LLM 
proposals. The GitHub token is read from the `COPILOT_GITHUB_TOKEN` environment variable;

For each `ParticleLLM` instance, the code creates a `CopilotClient` with the token, starts the client, and opens a Copilot session using the configured model (currently `GPT-5.6 Luna`). The session is reused for subsequent proposals from that particle and is stopped when the optimizer closes the particle. A missing token or SDK raises an error; a request timeout returns no proposal, and an empty, invalid, or incomplete response falls back to the particle's current position.

During each optimizer iteration, every particle sends one prompt containing its current basket, personal-best basket, swarm-best basket, their fitness context, PSO influence weights, and the candidate product catalog. The model is asked to return only a JSON object containing exactly 55 valid catalog item IDs. The response is parsed and validated locally before it can replace the particle's position. Consequently, a run with `N` particles and `I` iterations can make up to `N × I` Copilot proposal calls, subject to early stopping and failures.

## Repository files
- `family_pso_optimizer.py` — CLI, swarm initialization, evaluation, loop, and JSON report generation.
- `particle_llm.py` — per-particle Copilot session, prompt construction, response parsing, and validation.
- `utils.py` — data classes, catalog loading, family profiles, and health scoring.
- `config.py` — paths, defaults, PSO coefficients, and health keywords.
- `data/kaufland_prices_by_category_various_countries.json` — catalog input. 

## Python scraper and catalog data
The Python scraper in `data/kaufland_scraper.py` downloads the current Kaufland weekly-offers page and extracts the embedded offer data. It currently uses the German (`DE`) source, prioritizes food categories, removes duplicate offers, and can include additional categories when needed to reach the requested limit. The scraper-specific dependency is `requests`; its usage and options are documented in `data/README.md`.

The generated JSON catalog contains product names, prices and currencies, unit or base-price text when available, categories, source URLs, collection timestamps, validity dates, and country information. The optimizer loads this catalog as candidate products, addresses them by item ID, and selects a 55-ID family basket. Product prices contribute directly to fitness, while product and category text is also used for the lightweight keyword-based health penalty. Offer prices and availability reflect the current promotion cycle and may change when the scraper is run again.

The optimizer does not use sentence-transformer embeddings or a separate `family_llm.py` module.
